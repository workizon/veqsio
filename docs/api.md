# REST API reference

Veqsio exposes a Jira-compatible REST API. The reference is generated from the running server, so it cannot drift from
the code:

| What | Where |
|---|---|
| OpenAPI 3.1 document | `GET /rest/api/2/openapi.json` (public, cacheable, contains no instance data) |
| Browsable reference | `/api-docs` in the web app (public; built-in viewer: tags, endpoints, parameters, request bodies, responses, schemas, filter box) |
| Source of the hand-written part | `packages/api/src/openapi/handwritten.ts` |
| Generator | `packages/api/src/openapi/spec.ts` |

```bash
curl -s https://your-instance/rest/api/2/openapi.json | jq '.paths | keys | length'
```

You can feed the document to any OpenAPI 3.1 tool (Swagger UI, Redoc, openapi-generator, Postman, Bruno). Nothing in it is
specific to your instance: the server list is the relative URL `/`.

## How the document is built

1. **Every route in the Hono route table is listed** (path, method, path parameters, tag, authentication scheme, standard
   error responses). A route can therefore not be forgotten: the test `tests/integration/openapi.api.ts` fails when a
   documented path is missing from the route table, when a hand-written entry no longer matches a route, or when a route
   is missing from the document.
2. **Hand-written entries add the substance** for the most important endpoints: authentication, projects, issues,
   comments, JQL search, transitions, filters, boards and sprints, outgoing webhooks, inbound webhooks, the public API and
   the agent run API. They carry request bodies, response schemas, query parameters and prose. In the document these
   operations have `x-documented: handwritten`; the others have `x-documented: generated`.
3. Authentication is derived: operations in the public allowlist (the same list the security test suite enforces) have
   `security: []`; webhook receivers use the `webhookSignature` scheme; `/metrics` uses `metricsToken`; everything else
   accepts the `session` cookie or a bearer token.

## Authentication in one minute

```bash
# 1. a session cookie
curl -i -c cookies.txt -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"..."}' https://your-instance/rest/auth/1/session
# 2. use it
curl -b cookies.txt 'https://your-instance/rest/api/2/search?jql=project%20%3D%20PROJ%20ORDER%20BY%20created%20DESC'

# or a personal access token (Profile > Tokens), preferred for scripts
curl -H "Authorization: Bearer $TOKEN" https://your-instance/rest/api/2/myself
```

Errors are `{"errorMessages": ["..."]}`. A resource the caller may not see answers **404**, not 403. Requests are rate
limited per user and per address (429 with `Retry-After`). Every response carries `X-Request-Id`; quote it in bug
reports and send your own `X-Request-Id` (8-64 characters of `A-Za-z0-9._-`) to correlate with your logs.
