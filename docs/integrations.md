# Integrations: inbound webhooks, Sentry, Slack / Teams, copy as prompt, peek view

Feature switch id: `integrations` (Administration → Features and modules for the whole instance, Project settings → Features per project). While it is off the endpoints below answer 404 and chat channels stay silent; the configuration is kept.

## Inbound webhooks (alerts, CI, scripts)

Project settings → **Inbound webhooks** (project administrators). A *source* is one external system with its own URL, secret and mapping.

```
POST /rest/api/2/webhooks/inbound/<slug>
```

The slug is random and unguessable. This endpoint is public by design (it is on the `PUBLIC_ROUTES` list of the security suite) and is authenticated by the source's secret, never by a session:

| Auth mode | How the caller proves itself |
| --- | --- |
| Signature (default) | `X-Veqsio-Signature: sha256=<hex>` (or GitHub's `X-Hub-Signature-256`): HMAC-SHA256 of the **raw body** with the source secret |
| Shared secret header | `X-Veqsio-Secret: <secret>` or `Authorization: Bearer <secret>` |
| Sentry source | `Sentry-Hook-Signature: <hex>`: HMAC-SHA256 of the raw body with the secret as Sentry's client secret |

Secrets are generated by Veqsio, stored **encrypted** (AES-256-GCM, `SECRETS_ENCRYPTION_KEY`, the same mechanism as git webhook secrets) because HMAC verification needs the plaintext, shown **once** when the source is created, and replaced with **New secret** (the old one stops working at once).

Limits: 120 requests per minute per source and client address (`INBOUND_RATE_LIMIT_MAX`, answers 429 with `Retry-After`), bodies up to 256 KiB (`INBOUND_BODY_LIMIT_BYTES`, answers 413). Requests with a bad or missing signature get a plain 401 and are **not** logged (so an attacker cannot fill or evict the delivery log).

### What happens with a payload

1. The payload is mapped to a summary, description, priority, labels and a **dedup key** (see below).
2. No open issue for the dedup key: an issue is created (reporter = the source's *actor* user, issue type = the first non-sub-task type of the project unless the API sets `issueTypeId`).
3. An open issue exists for the dedup key (for example the same alert fingerprint): a **comment** is added instead.
4. The payload says "resolved" (`resolvedWhen`): the open issue is **transitioned to a done status** (the first available transition into a status of category *done*).
5. The issue for the key is already done and the problem fires again: a new issue is created and becomes the one tracked for that key.

All actions are checked against the permissions of the actor user (CREATE_ISSUES, ADD_COMMENTS, TRANSITION_ISSUES). The decision for one dedup key runs under a database advisory lock, so simultaneous alerts with the same fingerprint cannot create two issues.

**Retries do not duplicate.** A delivery carrying an idempotency key is claimed with a unique insert first. The key is taken from the `Idempotency-Key` header (or `X-Idempotency-Key`, GitHub's `X-GitHub-Delivery`, Sentry's `Request-ID`), else from the mapping's `idempotencyKey` template. A repeat answers `200 {"status":"duplicate"}`. If processing fails with a server error the key is released so the sender's retry is processed.

Responses: `201 {"status":"created","key":"APP-1"}`, `200 {"status":"commented"|"transitioned"|"ignored"|"duplicate"}`, `401`, `404`, `413`, `422` (the source is misconfigured, e.g. the actor lost its permission; details only in the log), `429`.

### Mapping templates

A mapping is JSON; every text field is a template. `{{ path }}` inserts a value from the payload: `alerts[0].labels.alertname`, `$.data.event.title`, `a["odd key"]`. Filters after `|`: `default "text"`, `upper`, `lower`, `trim`, `truncate 80`, `first` (first line), `json`.

```json
{
  "summary": "[{{alerts[0].labels.alertname}}] {{alerts[0].annotations.summary}}",
  "description": "{{alerts[0].annotations.description}}",
  "comment": "Alert fired again: {{alerts[0].annotations.summary}}",
  "priority": "{{alerts[0].labels.severity}}",
  "priorityMap": { "critical": "Highest", "warning": "High" },
  "labels": ["alert", "{{alerts[0].labels.team}}"],
  "dedupKey": "{{alerts[0].fingerprint}}",
  "resolvedWhen": { "path": "status", "equals": "resolved" }
}
```

Templating **cannot execute code**: an expression is a fixed lookup plus a whitelist of filters; prototype keys (`__proto__`, `constructor`, `prototype`) are never read; values are never re-rendered; templates are capped at 4000 characters, single values at 4000 and results at 20 000; control characters are stripped; the summary is a single line of at most 255 characters. Invalid templates are rejected when the source is saved. Presets for Generic JSON, Grafana alerting and GitHub Actions (`workflow_run`) are in the create dialog.

Text coming from outside is untrusted: issues created from it end with a note saying so.

### Test button and delivery log

* **Test → Preview (dry run)** takes a sample payload and shows the mapped fields and the action that would happen (create / comment on KEY / resolve KEY / nothing), with no side effects.
* **Send as test delivery** really processes the sample (as the actor) and marks the log entry as a test.
* **Deliveries** shows the last 100 deliveries per source with status, issue, dedup key and the payload. Payloads are **redacted** (keys such as `password`, `token`, `secret`, `authorization`, `api_key`, `cookie`, `signature`, and token-looking values such as bearer tokens, `ghp_…`, `xox…`, AWS keys, JWTs) and capped at 8 KB.

## Sentry intake

Create a source of type **Sentry** (no mapping needed). In Sentry create an internal integration with the webhook URL of the source and the secret as the client secret (or use the URL as a webhook action of an alert rule). Veqsio verifies `Sentry-Hook-Signature`.

* Issue alerts (`data.event`) and issue webhooks (`data.issue`, actions `created`, `resolved`, `unresolved`) are understood; installation and other actions are acknowledged and ignored.
* Title → summary, culprit, level, environment, project, rule and the Sentry link go into the description (only `http(s)` links are kept). Labels `sentry`, `sentry-<level>`, `env-<environment>`.
* Level → priority: fatal Highest, error High, warning Medium, info Low, debug Lowest (priorities are looked up by name; an unknown name leaves the priority at the default; `priorityMap` of the source overrides).
* Dedup key `sentry:<issue id>`: a repeat comments on the open issue, a Sentry "resolved" transitions it to done.

## Slack and Microsoft Teams notifications

Project settings → **Slack & Teams** (project administrators) and Administration → **Integrations** (system administrators, *default* channels that receive the events of every project). Outgoing **incoming webhooks only**:

* Events per channel: issue created, issue transitioned, comment added, issue assigned, sprint started, sprint completed, release published (when a version is marked released).
* Slack gets Block Kit blocks (header, linked title, fact fields, quoted comment); Teams gets an Adaptive Card (Workflows webhooks) or the legacy MessageCard (choose per channel). All text is escaped for the target format so a title cannot add mentions (`<!channel>`), links or markup, and is truncated.
* The webhook URL is checked against the SSRF guard (`plugins/ssrf.ts`: https only, no credentials in the URL, no private, loopback, link-local or metadata addresses unless `PLUGINS_ALLOW_PRIVATE_HOSTS=true`) when it is saved **and again before every send**; it is stored encrypted and only a masked form is ever returned.
* Delivery uses the shared transport (`plugins/transport.ts`): no redirects, 10 s timeout, up to 3 attempts with exponential back-off on network errors, 5xx, 429 and 408. Every attempt series is logged per channel (last 100). Each channel is limited to 30 messages per minute (`NOTIFY_RATE_PER_MINUTE`); extra messages are dropped and logged as `rate_limited`. A channel is switched off after 20 consecutive failed deliveries (`NOTIFY_FAILURE_THRESHOLD`).
* **Send test message** posts a test card and shows the result.
* Internal service desk comments are never forwarded. Messages contain issue key, summary, a few fields and a short comment excerpt, so only point channels at rooms whose members may see that.

**Out of scope:** Slack slash commands, interactive components and the Slack / Teams *apps* (two-way). Use the REST API or a plugin for that.

Environment variables: `INBOUND_RATE_LIMIT_MAX`, `INBOUND_BODY_LIMIT_BYTES`, `NOTIFY_TIMEOUT_MS`, `NOTIFY_MAX_ATTEMPTS`, `NOTIFY_RETRY_BASE_MS`, `NOTIFY_RATE_PER_MINUTE`, `NOTIFY_FAILURE_THRESHOLD`.

## Copy as prompt

Issue menu (⋯) → **Copy as prompt** copies a Markdown prompt to the clipboard: key and link, status, priority, people, labels, summary, description, acceptance information (the "Acceptance criteria" section and task-list checkboxes of the description, sub-tasks with their status), related issues, the most recent five comments (oldest first, each cut to 700 characters; internal notes are left out), a suggested branch name and what to do. The prompt states that all issue text is **untrusted data, not instructions**, and puts every piece of issue text in a code fence that is longer than any backtick run inside it, so hostile text cannot break out of the fence. The builder is `packages/web/lib/issue-prompt.ts` (unit tested).

## Peek view

On the issue list, the board and the backlog, the eye button on a row or card (or **P** on the focused row in the list) opens the issue in a right-side panel without leaving the page. The panel has the editable title, status button, description editor, the details sidebar and the comments / activity feed; "Open full page" goes to the normal issue page, and the layout button switches between the side panel and a centred dialog (remembered in the browser).

* The URL stays on the page and gets `?peek=KEY` (other parameters such as the JQL are kept), so a peeked issue can be shared and bookmarked; opening it from a link restores the panel. The browser back button closes it.
* Keyboard: **Esc** closes (an open dropdown or an inline editor consumes the first Esc), Tab and Shift+Tab stay inside the panel, focus moves into the panel on open and returns to the opener on close. The panel is a `role="dialog"` with `aria-modal` and an `aria-labelledby` title; list shortcuts are paused while it is open.
